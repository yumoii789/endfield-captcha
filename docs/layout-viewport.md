## 六、手机视口全扫描（九关 × 4 视口）与 puzzle2 的一处真实缺陷

**方法**：`vpsweep.mjs` —— 九关各以 `?direct=1&lv=1` 打开，在 320×568 / 360×640 / 390×844（竖屏）与 844×390（横屏）四种真实手机视口下测：文档横向溢出、纵向内滚、以及**每个元素**超出视口右缘的最大值（用于定位可疑元素）。

### 六之二、发现并修复：puzzle2 手机宽度下棋盘框被拉伸、格子仅 30px

**症状**：手机宽度（≤414）下 puzzle2 的棋盘框被拉到 92vw，而 25 个格子仍挤在左侧 166px，框内留下约 178px 空白；≤360 时整个棋盘块还比视口宽约 3px，左缘（行提示列）被 `body{overflow-x:hidden}` 裁掉。**点击格子只有 30px**，低于触屏 44px 建议值。

**根因（两处冲突）**：

1. `puzzle2.html:548 cellSize()` 读 `core().CELL`，但 `CELL` 在全仓库**从未被赋值**（`grep -n "CELL" puzzle2.html` 只有这一处读取）→ 恒返回 30，`buildGrid()` 于是写出**内联固定**轨道 `repeat(cols,30px)`（:565-568）与 `cellwrap` 宽高（:574）。
2. 手机媒体查询 `@media (max-width:640px)` 里写了 `.grid{width:92vw}`（:155）——意图是手机上棋盘随屏放大，但内联固定轨道不会跟着变，于是只剩「框变宽、格子不变」。

**修复（两处，桌面零影响）**：

- `cellSize()`：当 `window.innerWidth<=640` 时按可用宽度反算格子尺寸，扣除行提示列 26 + 块间距 6 + 网格内边距 12 + 边框 2 + 列间距 `(cols-1)*4`；取 `max(30, fit)`，宽视口不进入该分支。
- `@media (max-width:640px)` 的 `.grid{width:92vw}` → `.grid{max-width:92vw}`，让棋盘框贴合真实格子宽度。

**修复后实测**：

| 视口 | 格子尺寸 | 棋盘宽 | 横向溢出 | 格子中心命中测试 |
|---|---|---|---|---|
| 320×568 | 30 → **46px** | 258 | 0 | `.cell` ✓ |
| 360×640 | 30 → **53px** | 293 | 0 | `.cell` ✓ |
| 390×844 | 30 → **59px** | 323 | 0 | `.cell` ✓ |
| 414×896 | 30 → **63px** | 343 | 0 | `.cell` ✓ |
| 768×1024 | 30px（**不变**） | 180（不变） | 0 | `.cell` ✓ |
| 1280×900 | 30px（**不变**） | 180（不变） | 0 | `.cell` ✓ |

**真实通关复验**（390×844 + 触摸仿真，`clear_p2.mjs 390 844 1`）：7/7 块落位、`solved=true illegal=0`、hub `{lv:1,stars:3}`、stats `pass:true`。

**安全性核查**：`CS` 的全部引用点（网格轨道 :565-568、cellwrap :574、`cellXY` :594、`spanW/spanH` :626-627、点击→格换算 :1025-1026）都是符号化引用，无硬编码 30 假设。

### 六之三、视口变化时重算尺寸（原「已知限制」已修）

初版修复只在**载入时**算一次尺寸，于是留下一个真实缺口：**先在横屏打开（innerWidth>640 走桌面分支 → 30px）再转竖屏**，格子仍是 30px，老问题复现——这在手机上是很常见的操作顺序。

**修复**：新增 `relayoutGrid()`（puzzle2.html:712-731）——`resize`（宽度真变化时去抖 180ms）与 `orientationchange`（去抖 260ms）触发；**仅当新算出的尺寸与当前 `CS` 不同**才执行 `CS=cs; buildGrid(); refreshSelection(); refreshCounts();`（`refreshSelection()` 内部已含 `renderPlaced()`，故已放置的块会自动重绘）。

**验证（`p2relayout2.mjs`，触摸事件 + 真实放置）**：

| 步骤 | CS | 横向溢出 | 已放置 | 已渲染 .blk |
|---|---|---|---|---|
| 竖屏 390×844 载入 | 59 | 0 | 0 | 0 |
| 放第 1 块（p0 @0,0） | 59 | 0 | 1 | 1 |
| **旋转到横屏 844×390** | **30**（重算） | 0 | 1（保留） | 1（保留） |
| 旋转后放第 2 块（p1 @2,0） | 30 | 0 | 2 | 2 |
| **转回竖屏** | **59**（重算） | 0 | 2（保留） | 2（保留） |
| 放第 3 块（p2 @2,1） | 59 | 0 | 3 | 3 |

即：尺寸随视口重算、已放置的块不丢、旋转后交互照常。

**残留（记录在案，未改）**：横屏 844 宽时按设计走桌面分支（30px 格子），与 §六之一 记录的「横屏 86px 内滚」同属「竖屏才是设计目标」的取舍——此前对同类宽视口改动（§四）用户已选择保留原观感，故未扩展媒体查询条件。
